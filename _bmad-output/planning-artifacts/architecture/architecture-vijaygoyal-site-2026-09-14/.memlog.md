- (question) PARADIGM (first load-bearing call, precedes the framework fork): does the WebGL subject survive the redesign at all? Everything else — bundle cost, Lighthouse headroom, framework stakes, mobile strategy — follows from this.
- (decision) PARADIGM [ADOPTED by user 2026-09-14]: the WebGL narrative survives. One persistent 3D subject whose pose is a pure function of scroll position; chapters declare state, not scenes. Binds: every section's motion and the whole asset pipeline. Prevents: a section author inventing a second animation system or a second copy of the device.
- (decision) Stay on Vite; do NOT migrate to Next.js. Derived from the paradigm choice rather than asserted: react-three-fiber is client-only so App Router would make the whole page client components (spec section 74 warns against exactly that); SSR/ISR/image optimisation have nothing to act on for a canvas; the site is static with two case-study pages and needs no server; and Cloudflare's own recommended Next.js-on-Workers path is vinext, a Vite plugin at 94% API coverage. Binds: build tool, deploy path, component model. Prevents: a rewrite that discards the a11y/reduced-motion/context-loss layer and 202 tests for no capability gain.
- (constraint) Choosing the WebGL paradigm keeps the 959kB three.js chunk and therefore keeps the Lighthouse performance target (spec section 57, 90+) under pressure. Currently median 0.91 against a 0.90 floor, ~250ms TBT from ~810ms script evaluation. This is now a constraint to design around, not an argument to revisit.
- (question) HERO vs TBT tension: the canvas currently mounts at load, which is what spends the script-evaluation budget before first paint. Deferring it would fix TBT but spec section 15 wants both devices prominent in the hero immediately. Needs a decision on how the hero behaves before the canvas is ready.
- (decision) HERO [ADOPTED by user 2026-09-14]: poster-first. The hero ships a real static still, exported from the scene itself, as the LCP element. The canvas mounts after first paint and takes over. Binds: what the hero renders before hydration, and the Lighthouse budget every later section inherits. Prevents: a section author mounting the canvas eagerly and silently spending the pre-paint script budget.
- (decision) The poster is GENERATED FROM THE SCENE, never hand-made, so it cannot drift from the frame the canvas resolves to. Binds: the asset pipeline. Prevents: a stale poster that visibly snaps when the canvas takes over.
- (decision) Lighthouse performance 90+ stays a real target rather than being documented away. Derived: the user chose the only option that preserves both an instant-premium hero and the score, so the number matters to them.
- (question) MOTION OWNERSHIP — the spine's most important invariant: who owns scroll? The spec prefers GSAP ScrollTrigger (sections 12/13); the existing engine owns a ScrollDriver plus scroll-as-pure-function with POSES continuity validation. Spec section 60 warns about scroll libraries fighting. Two sections built independently could trivially diverge here.
- (decision) MOTION OWNERSHIP [ADOPTED by user 2026-09-14]: single owner. Scroll position stays the one source of truth; every animation is a pure function of one normalised progress value. NO GSAP, no ScrollTrigger, no Framer Motion, no Lenis. Nothing may own scroll except the engine's ScrollDriver, and nothing may change document height after layout. Binds: every section's motion, in all three spec motion tiers. Prevents: a second scroll owner whose pinning changes the progress denominator and silently desyncs copy from the 3D subject — the exact defect fixed on 2026-09-13.
- (decision) Declining the spec's preferred motion stack is documented rather than silent, as spec section 13 requires: GSAP is free as of April 2025 so cost is not the reason. The reasons are that a second scroll owner reintroduces the desync class of bug, that GSAP-driven subject state would destroy the pure-function property that makes the narrative testable headlessly in jsdom (how all 202 tests work), and that spec section 74 forbids installing a large animation framework for trivial effects — which is all the carve-out would have been.
- (question) SECTION MODEL: the spec's information architecture has 9 sections; the engine has 5 chapters with enter/exit poses and import-time continuity validation. Do the quiet sections (Process, Toolkit, About, Contact) join that model or sit outside it?
- (decision) SECTION MODEL [ADOPTED by user 2026-09-14]: extend the existing chapter model to all nine sections. Every section is a chapter with enter/exit poses; the quiet sections get poses where the subject has receded or left frame. Import-time continuity validation spans the whole page. Binds: how any new section is added — one folder, one registry line, two poses. Prevents: a section arriving with no defined subject state, or a second animation model growing in the lower half of the page.
- (constraint) Consequence of extending chapters to all nine: the subject must hold a sensible pose in every section, and the rotation budget plus the screen-only facing rule now apply to the whole page, not just the cinematic third. Continuity is validated across roughly ten poses rather than six. The canvas also stays mounted to the page foot — acceptable because frameloop is demand-driven, so an idle visitor costs no frames.
- (question) ROUTING AND CANVAS LIFETIME: spec section 48 adds /work/xbill and /work/shady-spade. A prior project decision is one canvas per session. Does the canvas persist into a case-study route, or are case studies canvas-free? Two builders could reasonably assume either.
- (decision) CASE STUDIES [ADOPTED by user 2026-09-14]: /work/xbill and /work/shady-spade are canvas-free reading experiences — static image-and-typography documents, no 3D, no three.js on the route. One canvas per session stays true because the canvas lives only on /. Binds: what a case-study page may import. Prevents: three.js being pulled onto a route that has no use for it, and a moving device competing with long-form prose.
- (decision) The change of register between home and case study is deliberate and must read as intentional: the shared design tokens carry the continuity instead of the motion. Binds: case-study styling. Prevents: two pages that look like two different sites.
- (question) ROUTE SERVING AND INDEXING: with real routes added, how are they served and indexed? Today not_found_handling=single-page-application makes every path return homepage HTML, so nothing 404s, robots.txt and sitemap.xml return HTML, and case studies would be client-rendered only.
- (decision) ROUTING [ADOPTED by user 2026-09-14]: client-side router for in-app navigation feel, AND every route prerendered to real static HTML at build. Not either/or — the router gives the transition, the prerender gives indexable markup, per-route metadata, shareable link previews and a page that works with JavaScript off. Binds: build output shape and how any new route is added. Prevents: a case study whose prose exists only after hydration.
- (decision) Cloudflare must serve a genuine 404 for unknown paths. not_found_handling=single-page-application is replaced now that real routes exist. Real robots.txt and sitemap.xml ship as files. Binds: wrangler.jsonc and the public/ contents. Prevents: soft-404s on every mistyped URL and robots.txt returning HTML.
- (decision) Prerendering / dovetails with the poster-first hero rather than fighting it: there is no WebGL in the build environment, so hasWebGL() is false and the prerendered HTML for / IS the existing StaticRoute — every chapter's copy, indexable, plus the poster. Hydration then upgrades it to the canvas. The a11y fallback and the SEO story become the same mechanism.
- (decision) The canvas unmounts on navigation away from / and remounts on return. One canvas per session still holds because only / ever has one. Binds: canvas lifecycle across routes. Prevents: a builder keeping it mounted-but-hidden on case-study routes to preserve state, which would put three.js back on those pages.
- (question) MOBILE: spec section 53 forbids replaying desktop scroll behaviour on mobile and wants it intentionally designed. With a single scroll owner and a pose-per-section model, what actually changes on a phone?
- (decision) MOBILE [ADOPTED by user 2026-09-14]: one narrative everywhere, tuned constants. Same chapter sequence and poses on every device; the existing quality tier scales dpr, anisotropy, light count and geometry smoothness. Mobile gets its OWN pacing constants — section lengths, rotation amounts, subject scale — never desktop's. Binds: every chapter's pacing and the tier table. Prevents: a second mobile narrative with its own poses to keep continuous, and desktop pacing shipped unchanged to a narrow frame.

Choosing one narrative for all devices makes this the single biggest untested assumption in the redesign. Must be resolved by real-device testing before launch, not by CI — CI throttles CPU only and does not model GPU fill rate.
